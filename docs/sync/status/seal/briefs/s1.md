## Build

Fill every `unimplemented!()` in `error.rs`, `entropy.rs`, `base32.rs`, `encodings.rs`, `keys.rs` and
`chain.rs`; check `ctx.rs` against the registry of §4.1, row by row. In detail:

1. `SealError::code` and the traits tests and callers need (`Debug`, `Clone`, `Copy`, `PartialEq`,
   `Eq`, `Display`, `std::error::Error`).
2. `OsEntropy` through `getrandom`; `FixedEntropy` (replays its bytes in order, fails with
   `seal/entropy` when they run out, passes `TEST_ENTROPY_MARKER` to `std::hint::black_box`).
3. Crockford base32 (§5.2) with private helpers for bit strings that are not whole bytes (the 10-bit
   and 20-bit checks of §17.2 and §18.1 are later callers); `relay_origin` with the host rules of
   §5.4; private validators for a host and a device name (§5.5) that tasks S2 to S5 will call.
4. Keys (§6): the recovery seed and its sheet text (§18: `to_sheet`, `from_sheet` with its four
   ordered steps and codes), the recovery keys and `dev_R`, `board_id`, device keys (generation order
   `dev`, signing key, X25519 `ikm`, as §17.10 "Draws" lists them), the identity bytes, epoch roots,
   commitments, `derive_epoch_key`, key fingerprints. The storage key and `K_file` are task S4's.
5. Wraps (§7): `wrap_root` and `unwrap_root`, HPKE base mode through the `hpke` crate with the
   ephemeral key pair `DeriveKeyPair(ikm)` from exactly 32 drawn bytes (SEAL-WRAP-004); the wrapper in
   `src/lib.rs`'s `const _` block shows how `Entropy` reaches hpke.
6. Chain and fingerprints (§15): `chain_zero`, `chain_step`, `sync_fingerprint`, `move_code`,
   `check_move_code`, `key_fingerprint`, `state_hash`.

Lead rulings:

- The word list is a copy inside the crate, `crates/taskdeck-seal/src/wordlist.txt`, embedded with
  `include_str!`; do not `include_str!` a file outside the crate. Tests check its SHA-256 and line
  count (SEAL-FP-002) and that it equals `docs/sync/spec/wordlist.txt` byte for byte.
- `DeviceKeys::to_identity_bytes` has no layout in a spec (`device.md` §6.4.7 only embeds it as
  `vb16`). Define one, fixed-width and versioned by its length, document it at the function, test the
  round trip and the rejection of every other length, and list it in your report as a spec question.
- `base32::decode_typed` has no error code of its own in §22: choose, say which, and list it.

## Tests and vectors

- Unit tests beside the modules; integration targets as `common.md` lays out. This task creates
  `tests/common/mod.rs` (hex helpers; no `hex` crate), `tests/kat/`, `tests/tamper/`, `tests/contexts/`,
  `tests/parsers/` and `tests/vectors/`, each `main.rs` with this task's module (`s1_*.rs`), written
  so that later tasks add a `mod` line and a file.
- `kat` (seal.md §24, last paragraph): RFC 8032 §7.1; RFC 9180 Appendix A for DHKEM(X25519,
  HKDF-SHA256), HKDF-SHA256, ChaCha20-Poly1305 in base mode; RFC 5869 Appendix A cases 1 to 3;
  draft-irtf-cfrg-xchacha-03 Appendix A; Wycheproof `ed25519_test.json` and
  `xchacha20_poly1305_test.json`. Fetch every vector from its official source with `curl` and extract
  it by program; never type a vector from memory. Sources that answered from this container:
  `https://www.rfc-editor.org/rfc/rfc8032.txt` (likewise 5869, 9180),
  `https://raw.githubusercontent.com/cfrg/draft-irtf-cfrg-hpke/master/test-vectors.json` (keep only
  the one suite, base mode),
  `https://datatracker.ietf.org/doc/html/draft-irtf-cfrg-xchacha-03`,
  `https://raw.githubusercontent.com/C2SP/wycheproof/main/testvectors_v1/<file>`. Keep the data under
  `tests/kat/` with a `README.md` naming each source, its licence, the date fetched and the SHA-256 of
  what was fetched. The tests exercise the pinned crates the way this crate calls them (strict
  verification for Ed25519; for RFC 9180 the key schedule, `enc` from `ikmE` and the first
  encryptions). Every Wycheproof case must give its expected result; report any you had to set aside
  and why.
- `tamper`: flipping any byte of a wrap, with every other input held, fails to unwrap; so does the
  right wrap under another board, epoch, commitment or recipient. `parsers`: property tests for
  `base32::decode_typed`, `RecoverySeed::from_sheet`, `DeviceKeys::from_identity_bytes`,
  `relay_origin`, `check_move_code` and `unwrap_root` over random and mutated inputs.
- `vectors`: the target and its write mode, with the families `seal-kdf.json`, `seal-wrap.json`,
  `seal-chain.json` and `seal-sheet.json` (§24's table says what each holds). `seal-chain.json` uses
  arbitrary byte strings as frames (the chain hashes any bytes).
- `crates/taskdeck-seal/ci.sh` (the contract is at the top of `scripts/ci/stage.sh`; it runs on Linux,
  Windows and macOS runners with `CI_OS` set, and by hand from the repository root):
  1. `cargo test --locked -p taskdeck-seal --features test-entropy`;
  2. `cargo clippy --locked -p taskdeck-seal --all-targets --features test-entropy -- -D warnings`;
  3. on Linux only: the three Android targets
     (`cargo check --locked -p taskdeck-seal --target aarch64-linux-android --target armv7-linux-androideabi --target x86_64-linux-android`),
     and SEAL-GEN-014: the library built with the feature contains `TEST_ENTROPY_MARKER` and the one
     built without it does not (search the built `.rlib`);
  4. the vectors' format: `bash scripts/gate-lib.sh vectors docs/sync/vectors`.
  It honours `CARGO_TARGET_DIR`, runs every step even after one fails, and exits 1 if any failed.
