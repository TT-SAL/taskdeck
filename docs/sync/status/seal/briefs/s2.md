## Build

Fill every `unimplemented!()` in `entries.rs` and `signatures.rs`, and the private pieces task S3's
`classify` will stand on:

1. Canonical JSON for this crate (lead decision L4: seal has no dependency on core, so it carries its
   own, private): an encoder over `serde_json::Value` that writes exactly `core.md` §4.2 (keys sorted
   as unsigned bytes by the encoder itself, never by relying on the map's order; compact; the string
   escapes of §4.2), and a strict parser that follows §4.5 and seal.md §5.3: valid UTF-8 JSON, depth
   at most 32, no duplicate key, no `null`, no number with a fraction or exponent, integers in range,
   and bytes equal to the canonical encoding of the parsed value (SEAL-ENC-003, SEAL-ENC-004).
2. `padded_len` (§10.2), the plaintext layout and unpadding with its five ordered checks (§10.3),
   `new_entry_id`, `seal_frame` (§8, §9; refuses `ctr = 0`, a `based_on` of seq 0 with a chain other
   than `C_0`, a payload over the cap; draws exactly the 24-byte nonce), `frame_hash`, `frame_header`
   (§14.2 step 1 only).
3. The payloads: `ctl_payload` with the inner signature (§11.3), `beat_payload`, `snap_payload`, and
   for every control item of §12 an encoder and a strict parser from and to the public structs. An
   encoder refuses a value its parser would reject.
4. The receive side as private functions, each returning the code §14.2 gives its step: the frame's
   layout (step 1), the signature under a given public key (step 4, strict), opening the envelope
   under a given key with the AD of §9.2 (step 10), unpadding (step 11), parsing a `ctl`, `beat` or
   `snap` payload with the inputs its table needs (the entry's seq, `based_on_seq`, the frame's epoch)
   and verifying the inner signature (step 15), and the shape of a list of items (§12.1, step 16).
   Document each at its definition: task S3 reads those comments.
5. Signatures (§16): `login_message`, `sign_login` (draws the 32-byte client nonce), `AdminOp::name`
   and `AdminOp::args` for every row of the registry, `admin_message`, `sign_admin`. A relay nonce that
   is not exactly 32 bytes is `seal/challenge_length`; an origin or host outside §5.4 is refused.

Lead rulings:

- Tests that need a private function are unit tests (`src/<module>/tests.rs`), property tests
  included: `proptest` is a dev-dependency.
- Where a public function cannot return an error but its input can be invalid (`AdminOp::args` with a
  host too long for `vb8`, a reinstatement with no wrap), the function that returns `Result`
  (`admin_message`, `sign_admin`) validates and refuses. Say in your report which code you chose where
  §22 names none.

## Tests and vectors

- Unit tests for: the canonical encoder and parser (every rejection of SEAL-ENC-004 by name), padding
  at the boundaries §10.2 lists, each of the five unpadding checks, every payload table and every
  control item table (each constraint violated once), the shapes of §12.1 (each accepted, near misses
  refused), each admin operation's bytes against a layout written out by hand in the test.
- Integration targets: `contexts` (a signature made for one of `frame`, `login`, `admin`, `ctl` does
  not verify as another, SEAL-CTX-002; task S4 adds `backup`); `parsers` (`frame_header` and the
  public builders over random and mutated inputs; the private parsers get unit property tests);
  `tamper` gets frames in task S3, when `classify` exists, so here a unit test flips every byte of a
  sealed frame and shows the signature check or the layout check fails.
- Vectors: `seal-frame.json`, `seal-padding.json`, `seal-signatures.json` (§24's table). A case that
  needs a private function (an unpadding error) is checked against the committed file by a unit test
  that reads the file.
